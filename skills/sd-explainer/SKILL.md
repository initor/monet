## Step 2: Generate interactive HTML simulation

**Parallelism:** The HTML generation can be decomposed into independent sub-agents:
- Sub-agent A: Generate CSS (theme, layout, animations)
- Sub-agent B: Generate JavaScript (state management, event handlers, interactivity)
- Sub-agent C: Extract and embed data (components/stories/problems/concepts as inline JSON)
Dispatch all three concurrently. Merge results into the final HTML template.

**Multi-concept parallelism:** If the user requests multiple concept explanations, each concept's simulation can be generated by a separate sub-agent concurrently. Dispatch one sub-agent per concept, then deliver the results as individual HTML files.

Generate a single self-contained HTML file with these sections:

### Header section

- Concept name as the page title and `<h1>`
- 2-3 sentence plain-English explanation of what the concept is and why it matters in distributed systems
- "How it works" summary as 3-5 bullet points covering the core algorithm or pattern

### Interactive simulation area

Build the simulation following these implementation guidelines:

**Visualization technology:**
- Use SVG for graph structures, tree structures, ring diagrams, and state machines (Consistent Hashing, Raft, Merkle Trees, Circuit Breakers, Vector Clocks, Leader Election)
- Use HTML5 Canvas for particle/flow simulations and animations with many moving elements (Backpressure, Rate Limiting, Load Balancing, Retry with Backoff, LSM Trees)
- Use a combination for concepts that need both (Bloom Filters: SVG for the bit array, Canvas for the animated hash functions)

**Layout:**
- Full-width simulation canvas/container taking at least 60% of viewport height
- Control panel below or beside the simulation with clearly labeled buttons, sliders, and inputs
- Stats/metrics panel showing live numerical data about the simulation state

**Animation:**
- Animate transitions smoothly using `requestAnimationFrame` for Canvas elements and CSS transitions/animations for SVG elements
- Include a **Speed slider** with 0.5x, 1x, and 2x options controlling animation speed
- Include a **Step-by-step mode** toggle: when enabled, the simulation pauses after each discrete step and shows a "Next Step" button. When disabled, the simulation runs continuously
- Include a **Reset** button that returns the simulation to its initial state

**Color coding (consistent across all explainers):**
- Green (`#22c55e`): healthy, active, success, accepted
- Red (`#ef4444`): failed, error, rejected, dead
- Yellow/amber (`#f59e0b`): transitioning, warning, pending, half-open
- Blue (`#3b82f6`): selected, highlighted, current focus
- Gray (`#6b7280`): inactive, disabled, background elements

**Labels and numbers:**
- Show node IDs, key values, timestamps, counters, and scores on all visual elements
- Use tooltips or hover states for additional detail on complex elements
- Annotate state transitions with the trigger or reason (e.g., "Failure threshold reached: 5/5")

### Concept-specific simulation details

Implement the simulation matching the concept. Below are detailed specifications for each concept. Implement ONLY the one the user requested.

**Consistent Hashing:**
- Draw a hash ring (circle) with nodes positioned by their hash values (0 to 2^32-1, normalized to 360 degrees)
- Keys shown as colored dots on the ring, assigned to the next clockwise node
- Buttons: "Add Node" (random hash position), "Remove Node" (click to select), "Add Key" (random or user-specified)
- When adding/removing nodes, animate key redistribution with arrows showing which keys move
- Toggle: "Virtual Nodes" -- show how virtual nodes (3-5 per physical node) improve distribution uniformity
- Stats panel: keys per node count, standard deviation of distribution, percentage of keys that moved on last operation

**Raft Consensus:**
- Display 5 nodes in a cluster, each showing their current state (Follower, Candidate, Leader) and term number
- Log entries visible for each node as a growing horizontal bar
- Buttons: "Send Client Request" (appends to leader log), "Kill Node" (click a node), "Restart Node", "Trigger Election Timeout" (on a specific follower)
- Visualize: heartbeats as small pulses between leader and followers, vote requests during elections, log replication messages
- Stats: current term, leader ID, committed log index, cluster health status

**CAP Theorem:**
- Three nodes with data stores, connected by network links
- Toggle: "Network Partition" (splits nodes into two groups)
- In no-partition mode: show both consistency and availability working (writes propagate, all reads return latest)
- In partition mode: show the tradeoff -- either reads block on partitioned side (CP) or reads return stale data (AP)
- Mode selector: CP system vs AP system behavior
- Visual: requests flowing in, responses flowing out, stale/fresh indicators on reads

**Vector Clocks:**
- 3 nodes displayed as vertical timelines (left to right: Node A, Node B, Node C)
- Each event shown as a dot on the timeline with its vector clock value displayed
- Buttons: "Local Event on A/B/C" (increments that node's clock), "Send Message from X to Y" (shows arrow between timelines, merges clocks)
- Conflict detection: when two events are concurrent (neither happened-before the other), highlight both in red with "CONFLICT" label
- Stats: current vector clock for each node, list of detected conflicts

**Merkle Trees:**
- Binary tree visualization with 8 leaf nodes (user can modify leaf values)
- Each node shows its hash value (abbreviated to 8 chars)
- Click a leaf node to change its value -- the tree recomputes hashes up to the root
- Color-code changed branches (nodes whose hash differs from a "reference" tree)
- Split view: "Local Tree" vs "Remote Tree" -- user modifies local, differences highlighted
- Stats: number of differing nodes, sync cost (number of nodes to transfer)

**Bloom Filters:**
- Bit array visualization (horizontal bar of cells, each 0 or 1, color-coded)
- Multiple hash functions shown (k=3 by default, adjustable 1-5)
- "Add Item" button with text input -- shows which bits each hash function sets
- "Query Item" button -- shows which bits are checked, returns "Definitely not in set" or "Possibly in set"
- False positive demo: add many items, then query absent items to see false positives occur
- Stats: fill ratio (bits set / total bits), expected false positive rate (calculated), actual false positive rate (measured)
- Slider: array size (64 to 1024 bits) -- show how size affects false positive rate

**LSM Trees:**
- Memtable shown as a sorted list at the top
- Multiple levels (L0, L1, L2) shown as rows of SSTable blocks
- "Insert Key" button with key-value input -- adds to memtable
- When memtable reaches threshold (configurable, default 4 entries), auto-flush to L0 SSTable
- "Trigger Compaction" button -- merge overlapping SSTables in adjacent levels with animation
- "Read Key" button -- shows the read path (check memtable, then L0, L1, L2) with visual highlighting
- Stats: memtable size, SSTables per level, read amplification, write amplification

**Backpressure:**
- Pipeline visualization: Producer -> Queue -> Consumer (3-stage flow)
- Producer rate slider (1-20 items/sec), Consumer rate slider (1-20 items/sec)
- Queue shown as a bounded buffer with visual fill level and capacity indicator
- When queue fills: show backpressure signal (red arrow back to producer), producer slows or drops items
- Three backpressure strategies (toggle): Drop newest, Drop oldest, Block producer
- Stats: producer rate, consumer rate, queue depth, items dropped, backpressure events

**Circuit Breakers:**
- State machine diagram: three states (Closed, Open, Half-Open) with transition arrows, current state highlighted and enlarged
- Request stream visualization below: incoming requests as dots, colored green (success) or red (failure)
- Buttons: "Send Request" (succeeds), "Send Failing Request" (fails), "Send Burst (10)" with success/fail ratio slider
- Configurable: failure threshold (default 5), timeout duration (default 5 seconds), half-open trial count (default 1)
- Timer visible when in Open state, counting down to Half-Open transition
- Stats: success count, failure count, consecutive failures, time in current state, total state transitions

**Rate Limiting:**
- Three panels side-by-side showing three algorithms simultaneously:
  - **Token Bucket:** Bucket visualization filling with tokens at a steady rate, each request consumes a token
  - **Sliding Window:** Time window visualization that slides, counting requests within the window
  - **Fixed Window:** Time window that resets at fixed intervals, counting requests within each window
- Buttons: "Send Request" (single), "Send Burst (10)" (rapid-fire)
- Configurable: rate limit (requests per window), window size (seconds), bucket capacity (for token bucket)
- Each panel shows accept (green check) or reject (red X) per request
- Stats per algorithm: accepted count, rejected count, current rate, window/bucket state

**Load Balancing:**
- Multiple backend servers (default 4) shown as boxes with health indicators and current load
- Request stream flowing in from the left
- Algorithm selector: Round Robin, Weighted Round Robin, Least Connections, Random
- "Send Request" button (single), "Send Burst (20)" button
- Server health toggle: click a server to mark it unhealthy (should be excluded from routing)
- Weight slider per server (for Weighted Round Robin)
- Stats: requests per server, response time distribution, current connections per server

**Retry with Backoff:**
- Timeline visualization showing a request attempt sequence horizontally
- Each attempt shown as a dot: green (success) or red (failure) with the wait time before the next attempt labeled
- "Send Request" button: starts a request that fails based on configurable failure rate
- Configurable: max retries (1-10), base delay (100ms-5s), failure rate (0-100%)
- Show: exponential backoff timing (base * 2^attempt), jitter (random offset visualized)
- Compare view: "No Jitter" vs "Full Jitter" vs "Decorrelated Jitter" side by side
- Stats: total attempts, total wait time, success rate

**Leader Election:**
- Cluster of 5 nodes in a circle, each with state (Leader, Follower, Candidate) and term number
- Current leader highlighted with a crown icon or border
- "Kill Leader" button: triggers re-election with timeout randomization visible
- "Kill Node" button: removes a follower from the cluster
- "Restart Node" button: brings a killed node back
- "Network Partition" button: splits cluster to demonstrate split-brain potential
- Heartbeat visualization: periodic pulses from leader to followers
- Stats: current term, leader ID, cluster size, quorum status

### Interview Application section

After the simulation, include a clearly separated section:

**Heading:** "How to Use This in an Interview"

Provide 2-3 example sentences showing how to articulate the concept to an interviewer. Format each as:

**Situation/context** -> **What you'd say**

Examples:

For Consistent Hashing:
- "When discussing data partitioning:" -> "I'd use consistent hashing for our cache layer. This means when we add or remove a node, only K/N keys need to redistribute rather than reshuffling everything, which gives us graceful scaling with minimal cache invalidation."
- "When asked about hotspot prevention:" -> "We can use virtual nodes -- each physical node maps to multiple positions on the ring, which smooths out the key distribution and prevents hotspots from hash clustering."

For Circuit Breakers:
- "When discussing service resilience:" -> "I'd add circuit breakers between our service and downstream dependencies. If the error rate exceeds our threshold, the circuit opens and we fail fast instead of cascading timeouts through the system, then automatically probe with half-open state to detect recovery."
- "When asked about cascading failures:" -> "Circuit breakers prevent cascade failures by isolating failing dependencies. The key insight is the three states: closed for normal operation, open for fast failure, and half-open to test if the dependency has recovered."

Include common interviewer follow-ups and strong answers for each example:
- **Follow-up:** "[Likely interviewer question]"
- **Strong answer:** "[How to respond]"

## Keyboard shortcuts (concept explainers)

- `Space` -- Pause/resume simulation
- `Right Arrow` -- Advance one step (when in step-by-step mode)
- `R` -- Reset simulation to initial state
- `+` / `-` -- Increase/decrease simulation speed
- `Escape` -- Close any open tooltip or info panel

## Constraints

- HTML must be completely self-contained -- all CSS and JS inline, no external dependencies (no CDN links, no imports, no fetch calls).
- Simulations must be truly interactive -- the user manipulates inputs and sees results. No passive animations or static diagrams.
- Each explainer should be educational enough that someone could learn the concept from scratch by reading the explanation and interacting with the simulation.
- Do not auto-trigger during mocks or drills -- this is on-demand only.
- Generated HTML should be under ~2500 lines. Focus on correct simulation behavior over visual polish.
- Step-by-step mode must be available for all simulations -- this helps users understand algorithm progression one discrete step at a time.
- Interview application sentences must be practical and ready to use verbatim in an interview.
- Always include the Reset button and Speed slider in every simulation.
- Color coding must be consistent across all explainers (green=healthy, red=failed, yellow=transitioning, blue=selected).
